# Тесты ToolBridge

## Организация тестов

- Если написание тестов ещё не согласовано, кратко опиши пользователю предлагаемые проверки, запроси явное подтверждение и дождись его.
- Проверки текущего функционала размещай в `ToolBridge.Tests.Core`. `ToolBridge.Tests` содержит общую инфраструктуру запуска и проверок; не добавляй в него тесты прикладных инструментов.
- Для каждого MCP-инструмента создавай отдельный файл и C#-класс с набором его тестов: `Tools/<Группа>/<Инструмент>Tests.cs`, например `Tools/AlgTools/GetAlignmentTests.cs`. Согласуй пространство имён со структурой каталогов. Общую подготовку данных выноси в фикстуру группы.
- Проверки совместимости с API 0.1.0 размещай в `ToolBridge.Tests.ApiCheck_v0.1.0`. Не меняй эталонные имена и сигнатуры старого API ради прохождения тестов текущей реализации.

## Работа с ToolBridge.Tests

- Используй ссылку на проект `ToolBridge.Tests`, атрибут `[Test]` и методы класса `Test` из пространства имён `ToolBridge.Tests`.
- Объявляй тесты непосредственно в классе как синхронные методы `void` без аргументов и параметров типа. Допустимы статические и экземплярные, публичные и непубличные методы. Асинхронные методы, включая `async void`, раннер не поддерживает; унаследованные методы не обнаруживает.
- Используй `Test.Require(condition, message)`, если при ошибке дальнейшие шаги не имеют смысла. Для независимых проверок, после которых выполнение должно продолжаться, используй `Test.Assert(condition, failureMessage)` или `Test.Fail(message)`.
- Проверяй ожидаемые исключения через `Test.Throws<T>(action)`: он принимает синхронное действие и возвращает исключение типа `T` или его наследника. Для значимых фрагментов диагностик используй `Test.RequireContains`; не фиксируй полный текст исключения без необходимости.
- `Test.Success` выводит сообщение об успехе, а `Test.Warning` — предупреждение без провала теста. Не заменяй предупреждением ошибку проверки или невыполненное обязательное условие запуска.

## Регистрация тестов

- Добавляй новые C#-файлы в `.csproj` элементами `Compile`: существующие проекты используют явный список исходников.
- Регистрируй каждый класс один раз в `Module.cs` тестового проекта: обработчик broadcast `test_request` добавляет экземпляр в `((List<object>)args[0])`. Не регистрируй `null` или несколько экземпляров одного типа.
- При создании нового тестового проекта подключи `ToolBridge.Tests` и текущий ToolBridge, добавь проект в `ToolBridge.Tests.sln`, настрой регистрацию обработчика в `.plugin` и копирование этого файла в выходной каталог. Для новых классов существующего проекта используй его обработчик регистрации.

## Подготовка данных и сценарии

- Каждый тест должен самостоятельно готовить данные и не зависеть от порядка запуска. Раннер использует один зарегистрированный экземпляр класса для всех его методов, поэтому не полагайся на состояние, оставшееся от другого теста.
- Создавай собственный DI-контейнер и подменяй сервисы доступа к работающей платформе локальными реализациями. Используй настоящие модели Robur, если их можно создавать изолированно; не изменяй контейнер и глобальные сервисы приложения.
- При проверке логики MCP-инструмента вызывай его метод напрямую и проверяй содержимое ответа через `JObject`/`JArray`. Проверки транспорта MCP и интеграции с работающим Robur выделяй отдельно и явно указывай условия запуска.
- Покрывай значимые успешные сценарии, граничные значения, неверные аргументы и ошибки зависимостей. Для изменяющих операций проверяй результат и состояние модели, а при отклонённом запросе — отсутствие нежелательных изменений.
- Освобождай ресурсы и восстанавливай изменённое состояние через `using` или `finally`. Если тест запускает параллельную работу, дождись её завершения; вызывай методы `Test` только из потока теста.

## Сборка, запуск и документация

- Используй .NET Framework 4.8 и реальные DLL Robur и его зависимостей из `robur-mcp/Out/Bin`, подключённые с `Private=False`. Сборки-заглушки без реализации методов не подходят для выполнения тестов.
- Собирай `ToolBridge.Tests.sln` вместе с текущим ToolBridge в общий каталог `Out/Bin`. Для запуска в Robur нужны актуальные DLL и файлы `.plugin`; команда запуска — `run_tests`.
- Учитывай условия конкретного набора: Core не требует открытого проекта или видового экрана; для `CheckInvocation` и `CheckContext` в ApiCheck нужен открытый видовой экран. Особенности автономного создания моделей чертежа описаны в README Core.
- При добавлении новых групп или изменении условий запуска актуализируй README тестового проекта; при изменении состава проектов — общий README. Сохраняй существующую стилистику документации.
