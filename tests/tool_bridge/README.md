# Тесты совместимости ToolBridge

[ToolBridge.Tests.sln](ToolBridge.Tests.sln) проверяет сохранение C# API, доступного плагинам, собранным против ToolBridge 0.1.0.

| Проект | Назначение |
| --- | --- |
| [ToolBridge.Tests](ToolBridge.Tests/) | Регистрация и запуск тестов, проверки `Test`, консоль результатов. |
| [ToolBridge.Tests.ApiCheck_v0.1.0](ToolBridge.Tests.ApiCheck_v0.1.0/) | Проверка контракта API 0.1.0 и интеграции старого провайдера с инфраструктурой ToolBridge. |

У каждого проекта собственный каталог `references`. Заглушки используются для компиляции и имеют `Private=False`; при запуске используются настоящие сборки Robur и ToolBridge.

## Сборка и запуск

1. Откройте `ToolBridge.Tests.sln` и соберите solution. Выходной каталог обоих проектов — `robur-mcp/Out/Bin` (`../../Out/Bin` относительно этой папки).
2. Установите в Robur обе DLL и файлы регистрации:

   | Сборка | Файл регистрации |
   | --- | --- |
   | `ToolBridge.Tests.dll` | `tool_bridge_tests.plugin` |
   | `ToolBridge.Tests.ApiCheck_v0.1.0.dll` | `tool_bridge_tests_api_check_v0.1.0.plugin` |

3. Выполните `run_tests` в Robur. Результаты появятся в отдельной Windows-консоли.

Для проверок вызова и контекста провайдера откройте видовой экран Robur. Если он отсутствует, эти две проверки завершаются ошибкой с указанием необходимого условия. Остальные проверки не требуют видового экрана. Останавливать MCP-сервер не требуется: тестовые инструменты не попадают в его коллекцию. Различие версий Newtonsoft.Json в зависимостях ожидаемо; предупреждение о конфликте можно игнорировать.

## Проверяемый контракт

Семь тестов соответствуют публичным типам API 0.1.0: `ToolProvider`, `ToolDefAttribute`, `ToolBridgeLogger`, `Services.ObjectStorage`, `JsonUtils`, `DwgUtils` и `SmdxUtils` в пространстве имён `Topomatic.ToolBridge`.

Контракт зафиксирован по метаданным заглушки версии 0.1.0.0 и охватывает 80 методов, конструкторов и аксессоров, а также объявления свойств. Проверяются:

- Полные имена и публичная доступность типов, базовые классы и возможность наследования.
- Доступность конструкторов, включая защищённый конструктор `ToolProvider`.
- Имена методов, перегрузки, статические и экземплярные члены, типы параметров и возвращаемые C#-типы.
- Свойства и доступность их getter/setter.
- Generic-параметры и ограничения, отсутствие новых абстрактных обязанностей у наследников `ToolProvider`.

Добавление членов API допускается. Тип возвращаемого значения проверяется как часть C#-сигнатуры; само значение не создаётся и не анализируется.

Проверки метаданных не выполняют методы, конструкторы и аксессоры ToolBridge.

## Интеграция старого провайдера

Шесть отдельных тестов проверяют работу провайдера, скомпилированного против API 0.1.0:

- Обнаружение через настоящий broadcast `tool_request` и регистрацию `.plugin`.
- Генерацию двух инструментов без `Domain`, отсутствовавшего в API 0.1.0, без вызова обработчиков.
- Создание и сортировку конфигураций этих инструментов, отдельно и вместе с сохранённой конфигурацией инструмента с доменом. Конкретный порядок сортировки не фиксируется.
- Наличие обоих инструментов по объявленным именам после инициализации менеджера.
- Передачу каждого вызова соответствующему обработчику ровно один раз.
- Заполнение `AppHost`, `CadView`, `SessionStorage` и `Logger` перед каждым вызовом; свойства проверяются внутри обработчиков.

Тесты не проверяют JSON-схемы, парсинг аргументов, ответы инструментов или прикладные исключения. Обработчики только фиксируют вызов и проверяют контекст. Файл пользовательских настроек не читается и не записывается; общие коллекции инструментов и конфигураций, а также объекты проекта не изменяются.

## Устройство проверок

Файлы проверок API содержат неизменяемые ожидания для соответствующих типов. Каждый тест использует `typeof` типа из ссылки на ToolBridge 0.1.0.0: удаление типа, смена пространства имён или невозможность разрешить старую ссылку проявляются при выполнении теста. `NoInlining` сохраняет отдельную границу вызова каждого тестового метода.

`ApiContract` читает метаданные фактически загруженных типов и проверяет сохранение требуемых членов без их вызова. Несовпадения записываются отдельно, чтобы один отсутствующий метод не скрывал остальные изменения того же типа.

`ProviderIntegrationChecks` содержит интеграционные сценарии. `LegacyToolProvider` объявляет инструменты через API 0.1.0 и регистрируется только в коллекцию собственного тестового broadcast. Ограничение регистрации снимается в `finally`, в том числе при исключении.

`IntegrationHost` изолирует reflection-доступ к текущей внутренней инфраструктуре. Каждый сценарий использует отдельные экземпляры провайдера, менеджера и коллекций. Проверка конфигураций вызывает `ToolConfigFactory.Create`, используемый также обычной загрузкой настроек; чтение файла настроек в этот сценарий не входит. Менеджер получает локальный набор инструментов через перегрузку `Initialize`.

Внутренние точки входа адаптера не являются частью эталонного API 0.1.0. При их рефакторинге обновляется адаптер; сигнатуры публичного API и объявления старого провайдера сохраняются.

Для проверки очередной версии ToolBridge используйте неизменную сборку ApiCheck, скомпилированную против заглушки 0.1.0, и меняйте установленный ToolBridge. Эталонные сигнатуры нельзя обновлять по текущей реализации: это скроет нарушения совместимости.

## Добавление тестов

Добавьте в проект ссылку на `ToolBridge.Tests`. Пометьте методы атрибутом `[Test]`: поддерживаются объявленные непосредственно в классе синхронные методы `void` без аргументов и параметров типа. Методы могут быть публичными или непубличными, статическими или экземплярными. Неподдерживаемые сигнатуры, включая `async void`, пропускаются с предупреждением.

Обработчик broadcast `test_request` получает в `args[0]` список `List<object>`. Добавьте в него новый экземпляр провайдера тестов и свяжите обработчик с broadcast в `.plugin`. Пример — [Module.cs](ToolBridge.Tests.ApiCheck_v0.1.0/Module.cs) и [файл регистрации ApiCheck](ToolBridge.Tests.ApiCheck_v0.1.0/tool_bridge_tests_api_check_v0.1.0.plugin).

Раннер выполняет классы и методы последовательно по именам в потоке команды Robur. Все методы одного блока используют зарегистрированный экземпляр. Повторная регистрация типа и `null` считаются ошибками регистрации. Запись результатов из фоновых потоков не поддерживается.

## Результаты

| Метод | Поведение |
| --- | --- |
| `Test.Assert(condition)` | Записывает успех или ошибку и продолжает выполнение. Перегрузка принимает отдельные сообщения для обоих исходов. |
| `Test.Require(condition, message)` | Выбрасывает исключение при ложном условии. |
| `Test.Success(message)` | Записывает сообщение об успехе. |
| `Test.Fail(message)` | Помечает текущий тест непройденным и продолжает выполнение. |
| `Test.Warning(message)` | Записывает предупреждение без изменения статуса теста. |

Необработанное исключение делает тест непройденным; следующие методы продолжают выполняться. Метод без ошибок считается пройденным. Для каждого провайдера выводится сводка пройденных, непройденных и пропущенных методов. Счётчики учитывают методы, а не отдельные проверки сигнатур; между блоками контекст сбрасывается.

Консоль открывается через встроенный Windows PowerShell. Закрытие окна не завершает Robur и не прерывает тесты. Вывод продолжается в фоне после завершения команды; при разрыве соединения консоль сообщает о возможной неполноте отчёта.
