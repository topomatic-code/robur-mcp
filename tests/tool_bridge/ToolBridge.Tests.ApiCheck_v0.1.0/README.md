# Проверки контракта ToolBridge API 0.1.0

Проект сравнивает публичный API текущего ToolBridge с неизменяемым эталоном версии 0.1.0 и проверяет интеграцию провайдера с текущей инфраструктурой. Он содержит семь проверок метаданных и шесть интеграционных сценариев.

[Общие инструкции по написанию и запуску тестов](../README.md).

## Зависимости и запуск

Проект ссылается на текущий `Topomatic.ToolBridge.csproj`. Сборки Robur подключаются из `robur-mcp/Out/Bin` с `Private=False`.

ApiCheck и общая инфраструктура `ToolBridge.Tests` подписываются существующим ключом `tool_bridge/Signature.snk`. Через `InternalsVisibleTo` основной проект предоставляет ApiCheck доступ к внутренним сервисам. Дополнительная сборка адаптера не требуется.

`Module` регистрирует `ApiChecks` и `ProviderIntegrationChecks` через broadcast `test_request`. Для запуска установите тестовую DLL, `tool_bridge_tests_api_check_v0.1.0.plugin` и общую инфраструктуру `ToolBridge.Tests` вместе с соответствующей сборкой ToolBridge.

Для `CheckInvocation` и `CheckContext` нужен открытый видовой экран Robur. Его отсутствие считается ошибкой условия запуска. Остальные проверки видового экрана не требуют. Останавливать MCP-сервер не требуется: тестовый провайдер регистрируется только в коллекции собственного проверочного broadcast.

## Эталон публичного API

Файлы `ApiChecks.*.cs` содержат ожидания для семи публичных типов версии 0.1.0: `ToolProvider`, `ToolDefAttribute`, `ToolBridgeLogger`, `Services.ObjectStorage`, `JsonUtils`, `DwgUtils` и `SmdxUtils` в пространстве имён `Topomatic.ToolBridge`.

Эталон получен из метаданных версии 0.1.0.0. Он охватывает 80 методов, конструкторов и аксессоров, а также объявления свойств. Проверяются:

- Полные имена и публичная доступность типов, базовые классы и возможность наследования.
- Доступность конструкторов, включая защищённый конструктор `ToolProvider`.
- Имена методов, перегрузки, статические и экземплярные члены, типы параметров и возвращаемые C#-типы.
- Свойства и доступность их getter/setter.
- Generic-параметры и ограничения, отсутствие новых абстрактных обязанностей у наследников.

`ApiContract` находит типы по эталонным полным именам в текущей сборке ToolBridge и сравнивает их метаданные. Отсутствующий тип записывается как ошибка. Несовпадения членов выводятся отдельно, чтобы одна ошибка не скрывала остальные. Эти проверки не вызывают методы, конструкторы и аксессоры проверяемых типов.

Добавление членов API допускается. Изменение старой сигнатуры, в том числе замена конкретного типа свойства интерфейсом, остаётся нарушением контракта. Эталон нельзя обновлять по текущей реализации ради прохождения тестов.

## Интеграционные сценарии

[ProviderIntegrationChecks.cs](ProviderIntegrationChecks.cs) содержит шесть проверок:

| Метод | Что проверяется |
| --- | --- |
| `CheckDiscovery` | Обнаружение провайдера через настоящий broadcast `tool_request` и регистрацию `.plugin`. |
| `CheckGenerationWithoutDomain` | Создание обоих инструментов без указания `Domain`, без вызова обработчиков. |
| `CheckConfigurationsWithoutDomain` | Загрузка, создание и сортировка конфигураций инструментов без домена, отдельно и вместе с конфигурацией инструмента с доменом. Конкретный порядок не фиксируется. |
| `CheckAvailability` | Наличие обоих инструментов по объявленным именам после инициализации менеджера. |
| `CheckInvocation` | Передача каждого вызова соответствующему обработчику ровно один раз. |
| `CheckContext` | Передача `AppHost`, `CadView`, `SessionStorage` и `Logger` перед каждым вызовом; ссылки проверяются внутри обработчиков. |

[ProbeToolProvider.cs](ProbeToolProvider.cs) объявляет два инструмента без `Domain`, как в API 0.1.0. Провайдер компилируется против текущего ToolBridge. Его обработчики только фиксируют вызовы и проверяют контекст. Временная регистрация отключается в `finally`, в том числе при исключении.

[IntegrationHost.cs](IntegrationHost.cs) готовит изолированное окружение и обращается к внутренним сервисам напрямую. Для менеджера создаётся отдельный настоящий DI-контейнер с локальным `IToolCollector`, выбранным видовым экраном, хранилищем и логгером. Вызывается штатный `ToolManager.Initialize()`.

Проверка конфигураций создаёт настоящий `ToolSettings` через DI. Его конструктор выполняет обычный `Load()`, включая объединение и сортировку конфигураций. Только `IToolConfigLoader` заменён реализацией в памяти; попытка сохранения завершает тест ошибкой. Файл пользовательских настроек и коллекции работающего сервера не изменяются.

## Границы проверки

Проверки подтверждают сохранение структуры публичного контракта 0.1.0 и работу текущей интеграции. Они не загружают плагин, заранее скомпилированный против старой DLL, и не дают полной гарантии бинарной совместимости такого плагина.

Тесты не фиксируют JSON-схемы, парсинг аргументов, ответы инструментов или прикладные исключения. Тип возвращаемого значения проверяется как часть C#-сигнатуры; само значение инструмента не анализируется.

При изменении DI-инфраструктуры обновляйте подготовку окружения и интеграционные сценарии. Эталонные имена и сигнатуры API 0.1.0 должны оставаться неизменными.
